## 与其他方向的关系

- **loop-engineering**：复杂 RAG 的多跳检索、查询分类路由本质是 agent 循环与工具编排；检索管线的验证闭环方法（评估先行、回归测试）与 loop 的 verify 同源。
- **graph-engineering**：GraphRAG/LightRAG 的索引-查询管线、批量 embedding 流水线是图编排（durable execution）的用武之地。
- **fde**：RAG 知识库治理是 FDE 交付的高频模块（`fde/` 最佳实践中的交付物清单）。
- **jev**：查询意图分类/路由等高频封闭判断可用判别模型承载（`jev/` 决策模型方向）。

## 五条最反直觉的结论（培训时先讲）

1. **模型越大越固执**：上下文与参数记忆冲突时，大模型回退记忆答案的比例更高（T5-11B ≥50%，NewsQA 案例高达 75%），数字型实体 ≥83% 不认新值——"以文档为准"必须做成系统机制，不能靠 prompt 一句话（01 §4.2）。
2. **召回不是越多越好**：top-k 从 20 再往上加，收益 ~1%而中间位置的文档甚至比不给文档还差（53.8% vs 闭书 56.1%）；正确姿势是"宽召回 + rerank 窄输出（3~6 条）+ 最相关放开头"（01 §1.3 / 02 §4.6）。
3. **"聪明"技巧可能降分**：query rewriting / query decomposition 在系统实验中反而伤害性能，分类路由才是双赢项——每个检索组件上线前先过评估（oracle gap / 自建评测集）（02 §5）。
4. **过滤 ≠ 授权，隔离 ≠ 鉴权**：检索过滤只是纵深防御层（AWS 全系免责声明），Milvus Partition/Partition Key、Pinecone namespace 都只有路由裁剪没有鉴权；权限必须服务端强制注入 + fail-closed 默认，"谁忘了拼过滤器谁就全量泄露"（05 §0/§1）。
5. **路由收益强依赖流量分布，路由器本身要快**：同一 RouteLLM 在闲聊分布省 73%、数学分布只省 33%；LLM 当路由器 = 每条请求多一次秒级往返，高频场景必须换 ms 级执行者（Semantic router ~10ms / SetFit / Laya 10.9ms）——意图识别选型的分水岭是"类目是否定型"而非"哪个模型更强"（06 §1~3）。
